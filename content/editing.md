## 1. 어떤 파일을 수정하나요?

사이트에 표시되는 문서 본문은 저장소의 **`content/` 아래 Markdown 파일**에서 읽습니다. 같은 내용을 HTML이나 React 코드에 다시 작성할 필요가 없습니다.

| 문서 | 수정할 파일 | 공개 주소 |
| --- | --- | --- |
| 회칙 | `content/bylaws.md` | [회칙](/bylaws/) |
| 재무 규정 | `content/finance.md` | [재무 규정](/finance/) |
| 재무 감사 시행세칙 | `content/audit.md` | [감사 시행세칙](/audit/) |
| 임원 선발 규정 | `content/recruitment.md` | [임원 선발 규정](/recruitment/) |
| 동아리방 이용 규정 | `content/clubroom.md` | [동아리방 이용 규정](/clubroom/) |
| 개인정보 처리방침 | `content/privacy.md` | [개인정보 처리방침](/privacy/) |
| 서비스 이용약관 | `content/terms.md` | [이용약관](/terms/) |
| 개인정보 동의서 | `content/consent.md` | [개인정보 동의서](/consent/) |
| 촬영·초상 이용 동의 | `content/media.md` | [촬영·초상 이용 동의](/media/) |
| CCTV 운영·관리 방침 | `content/cctv.md` | [CCTV 방침](/cctv/) |

이전 Jekyll용 `_includes/`, `_layouts/`, 각 문서 폴더의 `index.md`·`index.html`은 전환 전 자료입니다. **이전 파일을 수정해도 Next.js 사이트 본문은 바뀌지 않습니다.** 앞으로는 `content/`의 파일을 수정합니다. 비교용 원문과 보완 제안은 현행 문서와 구분하여 유지합니다.

## 2. GitHub에서 수정하고 반영하기

1. 저장소에서 수정할 Markdown 파일을 열고 연필 모양의 편집 버튼을 누릅니다. 수정 권한이 있는 계정으로 로그인해야 합니다.
2. 본문을 고친 뒤 미리보기와 변경 내용을 확인합니다. 조문 번호, 표의 금액·기간, 다른 문서 참조가 의도대로 유지되는지 점검합니다.
3. 변경 사유를 적어 `main`에 커밋합니다. 검토가 필요한 변경은 별도 브랜치의 Pull Request로 올린 뒤 검토 후 `main`에 병합합니다.
4. 저장소의 **Actions → Next.js Markdown Pages**에서 해당 커밋의 `build`와 `deploy`가 모두 성공했는지 확인합니다.
5. 공개 문서 페이지를 새로고침하여 변경 내용을 확인합니다.

**자동 반영 순서:** Markdown 수정 → `main` 커밋 또는 병합 → 문서 검사 → Next.js 빌드 → 결과물 검사 → GitHub Pages 배포 → 공개 버전 검증.

파일을 내 컴퓨터에 저장하거나 GitHub 편집 화면에서 입력만 한 상태는 공개 반영이 아닙니다. `main`에 저장된 변경의 배포가 성공한 뒤 공개 사이트가 바뀝니다. 열어 둔 브라우저 화면이 자동으로 바뀌는 실시간 공동 편집 방식은 아니며 새로고침이 필요합니다.

## 3. 문서 상단 정보와 본문

각 파일 맨 위의 두 `---` 사이에는 문서 정보를 적고, 그 아래에는 일반 Markdown 본문을 작성합니다.

```yaml
---
title: 개인정보 처리방침
description: 개인정보 처리 목적, 항목, 보유기간 및 권리 행사 기준.
status: 첨부 원문 기반 · 연락처 입력 필요
version: 'v1.1'
effective_date: '2026-09-01'
group: 정책
order: 6
source_type: source
---
```

위 코드는 형식 설명용 예시입니다. 실제 파일의 상태·버전을 무조건 이 값으로 덮어쓰지 않습니다.

`title`, `description`, `status`, `version`은 필수입니다. 날짜를 적는 경우 `YYYY-MM-DD` 형식의 문자열을 사용합니다. `group`과 `order`는 문서 목록의 분류와 순서를 지정합니다.

```markdown
## 제1조 목적

이곳에 조문 본문을 작성합니다.

### 세부 절차

1. 첫 번째 절차
2. 두 번째 절차

| 구분 | 내용 |
| --- | --- |
| 항목 | 설명 |
```

제목에서 문서 목차가 생성되고, 표·번호 목록·강조·링크가 웹 문서로 변환됩니다. 임의의 JavaScript나 MDX 실행 코드를 문서에 넣지 않습니다.

## 4. 시행일과 게시일 구분

기존에 지정한 규정의 시행일은 **2026년 9월 1일**입니다. 기술적 재빌드·재배포만으로 시행일이 오늘 날짜로 바뀌지는 않습니다.

실제 개정으로 시행일을 변경하는 경우 문서 상단의 `effective_date`뿐 아니라 **본문 부칙의 시행일, 버전, 변경 안내**도 함께 확인합니다. 재배포 자체는 문서 내용의 의결이나 회원의 동의를 뜻하지 않습니다. 원문에 비어 있는 담당자·연락처와 보충 작성안의 상태를 배포 과정에서 임의로 확정하지 않습니다.

이 운영 안내는 기술적인 편집 방법이며 회칙·약관의 새 조항이 아닙니다.

## 5. 새 문서 추가하기

`content/new-document.md`처럼 영문 소문자·숫자·하이픈으로 파일명을 정하고 필수 문서 정보와 본문을 넣습니다. `main`에 반영되어 배포가 성공하면 `/new-document/` 주소와 문서 목록이 자동 생성됩니다. 중첩 폴더도 사용할 수 있습니다.

예를 들어 `content/guide/example.md`의 공개 경로는 `/guide/example/`입니다. 파일명 변경은 공개 주소 변경이므로 이미 공유된 링크에 미칠 영향을 먼저 확인합니다.

`hidden: true`는 목록에서만 숨기는 설정이며 비공개 기능이 아닙니다. 이 저장소의 Markdown, 웹 문서, 다운로드 자료와 Git 이력은 공개된다는 전제로 작성합니다.

## 6. 배포 확인과 오류 처리

GitHub Actions의 실행 기록에서 **편집한 커밋과 배포한 커밋**이 같은지 확인합니다. 공개 사이트의 `/version.json`에는 사용된 소스 커밋, 문서별 해시, 전체 문서 해시와 빌드 시각이 기록됩니다. `/downloads/`에는 해당 배포에 사용된 Markdown이 제공됩니다.

문법 오류, 필수 정보 누락 또는 검증 실패로 `build`가 실패하면 새 결과물은 배포되지 않습니다. Actions에서 실패한 단계의 로그를 확인하고 파일을 수정하여 다시 커밋합니다. 배포 단계나 공개 버전 확인이 실패했다면 새 버전이 공개되었다고 단정하지 말고 실제 배포 상태를 확인합니다.

내용이 바뀌지 않은 채 재배포만 필요한 경우 **Actions → Next.js Markdown Pages → Run workflow → main**을 사용합니다. 변경을 되돌릴 때는 해당 Markdown을 이전 내용으로 복원하거나 되돌리기 커밋을 생성한 뒤 다시 배포합니다. 강제 푸시로 협업자의 기록을 덮어쓰지 않습니다.

## 7. 공개 저장소에 올리지 않는 자료

회원 명단, 생년월일·연락처 목록, 계좌 거래 내역, 서명된 동의서, 출입 비밀번호, 인증 토큰, CCTV 영상은 이 저장소에 저장하지 않습니다. 동의서 페이지에는 빈 서식과 안내만 게시하며 실제 개인정보 접수 기능은 제공하지 않습니다.
